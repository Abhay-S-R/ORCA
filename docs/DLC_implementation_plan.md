## 1. How to work this plan

**Pick points, not phases.** Whoever is free takes the lowest-numbered point in the current phase
whose dependencies are met and which nobody has claimed in the log. Claim it by writing a `CLAIMED`
entry in the log *before* starting. There is no per-developer allocation and no parallel track — if
two people are free at once, they take two different points that do not share files, or they ask.

**Phases are gates, not calendars.** A phase is finished when every point in it is `DONE` in the log
and the phase's exit gate passes. Do not start phase *n+1* points while phase *n* has open points,
unless a point in *n+1* is explicitly marked `PARALLEL-OK` — those touch no shared code and block
nothing.

**A point is done when its Done-when test passes, run by a human, not when the code compiles.**
The Done-when lines are lifted from the DLC's own `Accept:` criteria. If you cannot run the test,
the point is `BLOCKED`, not `DONE`.

**Principles that are not negotiable** — these come from the DLC and the PS doc, and a point that
violates one is wrong even if it passes its Done-when test:

1. **No fabricated values, ever.** A control whose data is unavailable is disabled and labelled
   MISSING. No number on screen that cannot be traced to a measurement. (`R-JUDGE-2`, `R-NEW-9`)
2. **No LLM in the safety path.** `risk_assessment.py` imports no LLM and `scripts/verify_ci_guards.py`
   must keep passing. If your change makes it fail, your change is wrong. (`R-JUDGE-4`, `R-AGENT-4`)
3. **Degrade loudly.** A fallback that is not disclosed is a lie. Position fallbacks, stale data,
   lost sessions, missing coverage — all say so before they say anything else. (`R-NEW-1`, `R-SAFE-1`,
   `R-AUTH-3`, `R-INDIA-8`)
4. **`data/` stays gitignored.** Fixtures are generated by scripts, never committed — not even to
   make CI pass.
5. **Every point serves a named PS clause or a named evaluation axis.** Both are recorded per point.
   Work that can name neither is scope creep and should be challenged in the log, not built.
6. **Run `graphify update .` after changing code**, so the next person's orientation is not stale.

## 2. The logging protocol

Open `docs/DLC_implementation_log.md` and append. Never edit someone else's entry; append a new one.

**Statuses:** `CLAIMED` → `DONE` · or → `BLOCKED` · or → `ABANDONED` · plus `NOTE` for anything else
worth the next person's time.

Every `DONE` entry must carry:

- the **point ID** and the **DLC R-ID(s)** it implements;
- **what changed**, as files touched — not a narrative;
- **how the Done-when test was run and what it showed.** "Tested" is not an answer; "ran
  `python -m pytest tests/unit/test_query_coverage.py`, 60 passed" is;
- **remarks** — the thing this file exists for. Anything the next person would otherwise rediscover:
  a wrong assumption in the DLC's `Now:` line, a dependency nobody predicted, a shortcut taken and
  why, a thing that looked done and was not.

**If you find the DLC is wrong**, say so in the log *and* correct the DLC in the same change. The DLC
is the source of truth; a source of truth with a known-false line in it stops being one. Record the
correction in your log entry so the change is traceable.

**If you deviate from a point's stated approach**, that is allowed — the DLC's `Required:` is a
specification, not an algorithm — but log the deviation and why. A silent deviation is the one thing
this protocol exists to prevent.
